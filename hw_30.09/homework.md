# Конспект: Протокол DHCP

## 1. Назначение и проблема

Для работы сети каждому сетевому интерфейсу (компьютера или маршрутизатора) необходим **IP-адрес**.

При ручном конфигурировании администратор:
- назначает IP-адрес и маску;
- указывает адрес шлюза по умолчанию, DNS-сервера, доменное имя и другие параметры TCP/IP;
- должен помнить, какие адреса уже заняты, а какие свободны.

Даже в небольшой сети это становится утомительной и подверженной ошибкам работой.

**DHCP** (Dynamic Host Configuration Protocol) — протокол динамического конфигурирования хостов. Он:
- автоматизирует назначение IP-адресов и других параметров;
- централизованно управляет пулом адресов и **гарантирует отсутствие дублирования**.

---

## 2. История: RARP → BOOTP → DHCP

### RARP (Reverse Address Resolution Protocol)
Одна из первых реализаций (более 30 лет назад).

Принцип работы:
1. Клиент отправляет широковещательный запрос.
2. Сервер находит в своей базе соответствие MAC → IP и отвечает.

**Недостатки:**
- сервер нужно было ставить в каждом сегменте сети;
- требовалась ручная регистрация всех MAC-адресов;
- невозможно было передавать дополнительную конфигурационную информацию.

### BOOTP (Bootstrap Protocol)
Создан на смену RARP. Изначально использовался для бездисковых рабочих станций.

Дополнительно передавал:
- адрес TFTP-сервера;
- имя загрузочного файла.

Важное нововведение — поддержка **relay-агентов** (посредников), которые пересылали запросы главному серверу. Это позволило одному серверу обслуживать несколько сетей.

**Ограничения:** ручная настройка таблиц и жёсткий лимит на размер дополнительной информации.

### DHCP
Современный протокол. Является **совместимым расширением BOOTP**.  
DHCP-сервер поддерживает устаревших клиентов BOOTP, но не наоборот.

## 3. Модель работы и режимы DHCP

DHCP работает по модели **клиент–сервер**.

При старте системы DHCP-клиент посылает широковещательный запрос. Сервер отвечает сообщением с IP-адресом и другими параметрами.

Администратор при настройке сервера указывает один или несколько диапазонов (пулов) IP-адресов одной сети.

### Три режима работы DHCP-сервера

| Режим | Описание | Соответствие IP ↔ клиент |
|-------|----------|---------------------------|
| **Ручное назначение** | Администратор жёстко привязывает IP-адреса к MAC-адресам (или другим идентификаторам) клиентов | Постоянное, задаётся вручную |
| **Автоматическое назначение статических адресов** | Сервер сам выбирает адрес из пула при первом обращении клиента | Постоянное, устанавливается при первом назначении |
| **Динамическое распределение** | Адрес выдаётся на ограниченное время (**срок аренды**) | Временное. После истечения аренды или ухода клиента адрес возвращается в пул |

---

## 4. Преимущества динамического распределения

Основное преимущество — автоматизация рутинной работы администратора.

Дополнительный эффект: можно построить сеть, в которой **количество узлов превышает количество имеющихся IP-адресов**.

### Пример
Организация с 500 мобильными сотрудниками, которые редко бывают в офисе. Обычно в офисе одновременно работает не более 50 человек.

- Без DHCP: нужно 500 адресов + 500 рабочих мест.
- С динамическим DHCP: достаточно пула из 64 адресов и 64 коннекторов.  
  Приходящий сотрудник просто подключает компьютер — клиент автоматически получает параметры от сервера.

## 5. Алгоритм динамического назначения адресов (упрощённо)

Администратор задаёт два основных параметра сервера:
1. **Пул адресов**.
2. **Срок аренды** (зависит от характера сети: от длительности лабораторной работы до нескольких недель).

DHCP-сервер обычно находится в одной подсети с клиентами (клиенты используют широковещание).  
Для отказоустойчивости можно поставить резервный сервер.  
Если сервера в подсети нет — используется **DHCP-relay-агент** (связной агент), который пересылает запросы на сервер в другой сети.

### Последовательность обмена сообщениями

1. **DHCP Discover** (поиск)  
   Клиент при включении отправляет ограниченный широковещательный запрос (адрес назначения — все единицы).

2. **DHCP Offer** (предложение)  
   Все DHCP-серверы (или relay-агент) получают Discover и отвечают предложением: IP-адрес + конфигурационные параметры.

3. **DHCP Request** (запрос)  
   Клиент выбирает одно из предложений (обычно первое) и отправляет широковещательный Request, указывая выбранный сервер и параметры.

4. **DHCP ACK** (квитанция)  
   Выбранный сервер подтверждает выделение адреса и параметров. Остальные серверы возвращают предложенные адреса в свои пулы.

5. Клиент получает ACK и переходит в рабочее состояние.

### Продление аренды и отказ

- Клиент пытается обновить аренду **задолго до её истечения**, обращаясь к тому же серверу.
- При неудаче повторяет попытки, затем обращается к другим серверам.
- Если никто не подтверждает — клиент теряет параметры и переходит в автономный режим.
- Клиент может **досрочно отказаться** от адреса (DHCP Release).

## 6. Проблемы динамических адресов и способы решения

Динамические адреса создают сложности:

1. **Преобразование имён (DNS)**  
   Таблицы DNS должны постоянно обновляться.  
   **Решение:** для серверов и важных устройств назначают статические адреса; для клиентов — Dynamic DNS (согласование баз DHCP и DNS).

2. **Удалённое управление и мониторинг**  
   Трудно обращаться к устройству, если его IP постоянно меняется.  
   **Решение:** статические адреса для маршрутизаторов, серверов, принтеров и других устройств с постоянным местоположением.

3. **Фильтрация и безопасность**  
   Сложнее настраивать ACL и правила фильтрации по IP.  
   **Решение:** отказ от динамических адресов для критически важных интерфейсов.

---

## Краткие выводы

- DHCP автоматизирует конфигурирование TCP/IP и исключает дублирование адресов.
- Основные режимы: ручной, автоматический статический, динамический.
- Динамический режим позволяет эффективно использовать ограниченный пул адресов (особенно при мобильных пользователях).
- Процесс выделения адреса: Discover → Offer → Request → ACK.
- Для серверов и критичных устройств предпочтительны статические адреса.
- Relay-агенты позволяют одному серверу обслуживать несколько подсетей.
